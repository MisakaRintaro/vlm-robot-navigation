# 設計書：言葉で指示できるロボット

## 1. 概要
「ピンクのテープのところへ行って」のように言葉で指示すると、ロボットがカメラで目標を探し、近づいて止まる。

- 画像と言葉の理解は、ロボット向けの VLM **Gemini Robotics-ER 2** が担当する
- 正確な移動と安全な停止は、センサ（オドメトリ・LiDAR）を使った自作の制御が担当する

講座の課題サンプル「Gemini Robotics-ER 1.6を試す」（画像の中の物を指させる）を出発点に、指させた結果で**実機を動かす**ところまで発展させる。

## 2. 要求

### 2.1 機能要求
| ID | 要求 |
|---|---|
| F1 | 起動時に、目標を言葉で1つ指定できる（例：`"ピンクのテープ"`） |
| F2 | カメラ画像と指示を Gemini に送り、目標が画像のどこにあるか（または見えないか）を得る |
| F3 | 正面の画像で見えないときは、車体を一周させながら首を振って画像を撮りため、まとめて1回の問い合わせで探す。それでも見えなければ、LiDAR で一番空いている方向へ少し移動して探し直す |
| F4 | 目標が見えたら、その方向に向いて少し前進する。これを繰り返して近づく |
| F5 | 目標が画像の下のほう（初期値：高さの 90% より下）に見えたら到着とし、停止してブザーで知らせる |
| F5' | 前方の障害物が一定距離（初期値：車体の先端から約 5cm）以内なら停止する（到着とは区別する） |
| F6 | 一定回数・時間で目標に着けなければ、諦めて停止する |
| F7 | 前方の障害物で止まったら、少し後退してから探し直す（後退時は後方の障害物も確認する） |

### 2.2 非機能要求
| ID | 要求 |
|---|---|
| N1 | **安全**：プログラムがどう終わっても（正常終了・Ctrl+C・異常）、ロボットを停止させる |
| N2 | **安全**：前方の障害物の判定は AI ではなく LiDAR で行う。ただし床の低い目標は LiDAR に映らないため、到着の判定には使わない |
| N3 | **記録**：うまくいかなかったときに原因を調べられるよう、AI の入出力とロボットの状態を記録する（7章） |
| N4 | **単純さ**：検証や例外処理を必要以上に増やさない。安全に必要な場合以外は、記録の失敗などでロボットを止めない |
| N5 | **再現性**：README の手順で、別の環境でも同じように動かせる |

## 3. システム構成

### 3.1 ハードウェア
| 部品 | 用途 |
|---|---|
| Yahboom MicroROS-ESP32 ロボットカー | 走行（`/cmd_vel`）、オドメトリ（`/odom_raw`）、ブザー（`/beep`） |
| MS200 LiDAR | 前方の距離（`/scan`、12 Hz） |
| ROS-WiFi カメラ（首振りサーボ付き） | 画像（`/espRos/esp32camera`、320×240 JPEG、約 7 Hz）。サーボは正面（0°）に固定する |
| PC（WSL2 + Docker、RTX 5060 Ti） | ROS 2 Humble・制御ノードを動かす。Gemini はクラウド API |

### 3.2 ソフトウェア（データの流れ）
```
                      ┌───────────────── 制御ノード（自作・1つ）──────────────────┐
カメラ ──画像─────────▶│                                                          │
ロボット ──/odom_raw──▶│  手順の管理：見る → 向く・探す → 進む → 見る … → 到着     │──/cmd_vel──▶ ロボット
LiDAR ──/scan────────▶│        │                                                 │──/beep─────▶ ロボット
                      │        └「見る」のときだけ ──画像＋指示──▶ Gemini（クラウド） │──/go_to/event（記録用）
                      └──────────────────────────────────────────────────────────┘
```
- ノードは1つにする。Gemini の呼び出しは、ノード内の関数で行う
- Gemini の担当は「目標が画像のどこにあるか」を答えることだけ。どのトピックに何を送るかは、制御ノードが決める（AI の誤りがあっても、速度の上限や停止判定はコードで守られる）

## 4. 動作

### 4.1 手順（状態）
```
【探す】正面の画像1枚を Gemini に送る
   └─ 見えない ──▶ [一周撮影] 車体を 90° ずつ回し、首を −20°・0°・+20° に振って 12 枚 → まとめて1回で送る
                     └─ 見えない ──▶ [移動] 十分空いている方向からランダムに選んで 30cm 進む ──▶【探す】
【近づく】見えた ──▶ 目標の方向へ旋回（撮影時の向き・首の角度・画像の位置から計算）
   ├─ 目標が画像の下のほう ──▶ [到着] 停止してブザー
   ├─ 旋回が 10° より大きかった ──▶ 進まずに見直す（旋回の誤差を打ち消す）
   └─ それ以外 ──▶ 前進（近いなら 10cm、遠いなら 30cm）──▶ 正面で見る
【見失った】
   ├─ 前進した直後 ──▶ [足元を見る] カメラを −60° に下げて見る。写っていれば [到着]
   └─ [詳細探索] 車体を 60° ずつ回し、首を −20°・0°・+20°、うなずきを −20°・−50° に振って 36 枚 → まとめて1回で送る
        └─ 見えない ──▶ 空いている方向へ 10cm だけ動いて、もう一度 [詳細探索]
             （続けて 3 回見えなければ【探す】に戻る）
 前方の障害物が停止距離以内 ──▶ [後退] 少し下がって見直す（続けて3回を超えたら [諦める]）
   ・目標を追っている途中なら、向きはそのまま（目標を見失わないため）
   ・目標が見つかっていないときは、LiDAR で一番空いている方向へ向き直す
 回数・時間の上限 ──▶ [諦める] 停止
```
- カメラは少し下向き（−20°）にする。床の物を視野に入れるため（初回の走行で、水平だと床の目標が映らなかった）
- 撮りためた画像はまとめて1回で送る。最初は首を振るたびに1回ずつ問い合わせていたが、問い合わせ1回に数秒かかり遅かったため
- 移動する方向は、一番空いている方向に固定すると同じ場所を往復しやすいため、十分空いている方向（最大の 6 割以上）からランダムに選ぶ
- 見失ったときは目標が近くにある可能性が高いので、角度を細かくし、足元寄り（−50°）も撮る詳細探索にする

### 4.2 AI が遅い問題への対処
Gemini の応答には約 3.5 秒かかる（実測）。
- **止まって考える**：問い合わせている間はロボットを止める。古い画像で走ることがない
- **速い処理はセンサで行う**：旋回角度は `/odom_raw`、前方の距離は `/scan` で常に（10 Hz）判断する
- **1回の答えでまとめて動く**：「向く＋少し進む」まで動いてから、聞き直す

## 5. AI（Gemini Robotics-ER 2）とのやりとり
| 項目 | 内容 |
|---|---|
| モデル | `gemini-robotics-er-2-preview`（2026-07 プレビュー公開） |
| 入力 | カメラ画像（JPEG。一周探索では12枚をまとめて）＋プロンプト |
| thinking_level | `medium`（公式推奨。速度と精度のバランス） |
| 出力 | 1枚のとき：`[{"point": [y, x], "label": "..."}]`、見えなければ `[]`。複数枚のとき：`{"image": 番号, "point": [y, x]}`、見えなければ `{}`。座標は 0〜1000 に正規化 |

プロンプト（`<target>` に指示が入る）：
```
Point to the <target> in the image.
Answer in JSON: [{"point": [y, x], "label": <name>}].
Points are [y, x] normalized to 0-1000.
If it is not visible, answer [].
```
- 車体を回す角度 ＝ 首の角度 ＋ 画像の横位置の分：`角度 = −首振り角 + (0.5 − x / 1000) × カメラの水平視野角`（左回りが正。首振りサーボは右が正なので符号を反転）
- **回数制限**：無料枠は 1 分に 5 回まで（初回の走行で `429 RESOURCE_EXHAUSTED` を確認）。有料プランに切り替えて間隔を 0 にした。無料枠で使う場合は、問い合わせ間隔を 12.5 秒以上にする（`QUERY_INTERVAL`）
- 首振りは ±60° だと回りすぎて機構に無理がかかったため、±20° にした
- 一周探索で見つけた場合は、撮影時の車体の向き（オドメトリ）を覚えておき、`回る角度 = 撮影時の向き − 今の向き − 首振り角 + 画像内の位置の分` で目標の方向を求める
- **API エラー時**：「見えない」とはみなさず、10 秒待ってから、動かずに同じ向きで聞き直す（初回は、エラーを見えない扱いにしたため、見ないまま旋回してしまった）

## 6. 安全設計
| 対策 | 内容 | 由来 |
|---|---|---|
| 走行指令を周期的に送る | 走行中は 10 Hz で `/cmd_vel` を送り続ける | `/cmd_vel` は最後の指令を保持し、1通落ちることがある（guide/02） |
| 停止を確認する | 終了時は、`/odom_raw` の速度が 0 になるまで停止を送る（上限 2 秒） | guide/04 の `drive_forward.py` |
| Ctrl+C でも止める | ROS の Ctrl+C 処理を無効にし、Python 側で受けて停止を送る | Humble の標準処理は通信を先に閉じるため（guide/04） |
| LiDAR で止める | 進む向き（前進なら前方、後退なら後方）が停止距離以内なら停止 | N2 |
| 障害物でのやり直しに上限 | 障害物で止まって後退するのは続けて 3 回まで | 同じ障害物での繰り返しを防ぐ |
| 後退後に向き直す（目標が見つかっていないときだけ） | 後退したあと、一番空いている方向へ旋回する | 向きを変えずに同じ壁へ何度も当たり、上限に達した（4回目の走行）。ただし目標に向かう途中で向き直すと目標を見失ったため（7回目の走行）、そのときは向き直さない |
| 動くときはカメラを下げる | 旋回・前進・後退の前に、カメラを −50° に下げる | カメラが −35° より上だと、カメラの頭が LiDAR の測定面に入り、正面を塞ぐ。どの向きでも「前方に障害物」となり、後退を繰り返した（6回目の走行後に実測） |
| 前後で止まる距離を分ける | 車体の端から 5 cm（前後で LiDAR から端までの距離が違う） | 後ろの端は LiDAR から 0.135 m あり、前と同じ設定では後ろの障害物で止まらなかった |
| LiDAR の近距離の値を捨てない | 有効とみなす最短距離を `range_min`（0.12 m）ではなく 0.03 m にする | 実機は 0.05 m まで安定して返す。`range_min` で捨てると 12 cm より近い物が見えず、止まる位置も推定より手前になっていた（5回目の走行後に実測） |
| LiDAR の外れ値を無視 | 範囲内で 2 点以上が近いときだけ物があるとみなす | 実機で 1 点だけの近い値（ノイズ）が出て、障害物と誤判定した（4回目の走行） |
| センサが途絶えたら止める | `/scan` や `/odom_raw` が 1 秒以上届かなければ停止 | 安全に必要な最低限の確認 |
| 速度の上限 | 前進 0.1 m/s、旋回 0.5 rad/s | 実験済みの速度 |
| 上限で諦める | Gemini の問い合わせ 40 回、または 600 秒で停止 | F6 |
| 動作の時間上限 | 旋回・前進が想定時間の 3 倍を超えたら停止 | 車輪の空回り・引っかかり対策 |

## 7. モニタリング・記録
講義（応用編1 第3回）の「症状 → 観測 → 比較 → 記録」に沿い、うまくいかなかったときに**何が起きたかを後から確かめられる**ようにする。記録は best-effort（失敗しても警告だけで、ロボットは止めない）とする。

| 種類 | 内容 | 使いどころ |
|---|---|---|
| ログ | 状態の切り替わり、Gemini の答え・応答時間、停止理由をログに出す（`get_logger`） | 実行中にターミナルや `rqt_console` で見る |
| イベントトピック | 上と同じ内容を JSON で `/go_to/event`（`std_msgs/String`）に publish | rosbag に、センサと同じ時間軸で AI の判断が残る |
| 実行記録フォルダ | `runs/<日時>/` に、Gemini に送った画像・指した点を描いた画像・やりとりの JSON を保存 | AI の誤りの確認、動画・レポートの素材 |
| rosbag | `ros2 bag record` で `/cmd_vel` `/odom_raw` `/scan` `/espRos/esp32camera` `/go_to/event` を記録（コマンドで実行。コードは書かない） | 「実験の真実の記録」（基礎編 第6回）。再生して rviz2・rqt_plot で見直す |
| 起動時の確認 | `/odom_raw` `/scan` カメラ画像が届くまで待つ（10 秒）。届かないものがあれば名前を表示して、走らずに終わる | ロボットの接続が不安定なため（安全に必要な最低限の確認） |

## 8. 設計時の主な考慮事項
| # | 考慮事項 | 方針 |
|---|---|---|
| 1 | ロボットの接続が不安定（電源 ON だけでは接続しないことがある） | 起動手順を README に固める。起動時の確認（7章）で検出する |
| 2 | AI の誤り（別の物を指す・ないのにあると答える） | 見えなければ探し直す。上限で諦める。記録で確認する |
| 3 | カメラの水平視野角が不明 | 実験で測る。誤差は「向く → 進む → 見直す」の繰り返しで吸収する |
| 10 | 近づくと目標がカメラの視野の下に外れ、「到着」と判定する前に見失う（8回目の走行） | 前進直後に見失ったら、カメラを下げて足元を確かめる |
| 12 | カメラ画像は WiFi 経由で遅れて届く。首振り・旋回の直後の画像は、動く前の向きのものであることがある（9回目の走行で、一周探索で見つけた方向へ回っても目標がなかった） | 動き終わってから 1 秒以上後に届いた画像だけを使う |
| 11 | 近いほど視野が狭く、旋回の誤差（視野角の仮定・回りすぎ）で目標が視野から外れやすい | 大きく回ったら進む前に見直す。近いときは 10cm ずつ進む |
| 4 | 床の平たい目標は LiDAR の測定面より低く、映らない（2回目の走行で、奥の物を測って到着と誤判定した） | 到着はカメラ（目標の縦位置）で判断する。LiDAR は障害物での停止だけに使う |
| 5 | LiDAR の「正面」が `/scan` の何番目のデータか未確認 | 実機で確認してから実装する |
| 6 | 画質が低い（320×240） | 目立つ色・形の物を目標にする |
| 7 | API の制限（無料枠は 1 分に 5 回）、画像が Google に送られる | 問い合わせ間隔をあける。人の顔や個人情報を映さない（初回の記録に手や腕が映っていた） |
| 9 | カメラが LiDAR の視界を塞ぐ（うなずき角 −35° より上のとき） | 見るときだけカメラを上げ、動くときは −50° に下げる |
| 8 | LiDAR では段差（机の端など）を検知できない。後退・移動時も同じ。机の外の遠い壁を「空いている」と判断しうる | 広い面で、人が監視しながら走らせる（自宅に走行できる床がないため、広い机の上で実施） |

## 9. 主なパラメータ（初期値。実機で調整する。[../src/vlm_nav/config.py](../src/vlm_nav/config.py) にまとめる）
| パラメータ | 初期値 |
|---|---|
| 前進速度 / 旋回速度 | 0.1 m/s / 0.5 rad/s |
| 1回に進む距離（遠い / 近い） | 0.3 m / 0.1 m（目標が画像の下半分なら近い） |
| 進む前に見直す旋回角 | 10° より大きいとき |
| 一周撮影：首振り / うなずき / 車体の旋回 | −20°, 0°, +20° / −20° / 90° ずつ（計12枚） |
| 詳細探索：首振り / うなずき / 車体の旋回 | −20°, 0°, +20° / −20°, −50° / 60° ずつ（計36枚）。見つからなければ 10cm 動いて再実行、続けて 3 回で通常の探索に戻る |
| 障害物で止まったときの後退距離 / やり直し上限 | 0.15 m / 続けて 3 回 |
| 見つからないときに移動する距離 / 方向の候補 | 0.3 m / 30° ごとのうち、一番空いている方向の 6 割以上空いている方向 |
| 問い合わせの最小間隔 | 0 秒（有料プラン）/ 12.5 秒（無料枠） |
| 到着とみなす目標の縦位置 | 画像の高さの 90% より下 |
| 障害物で止まる距離（進む向き） | 車体の端から 5 cm（LiDAR の中心から端まで：前 0.113 m、後ろ 0.135 m を実測） |
| カメラのうなずき角（見るとき / 動くとき / 足元を見るとき） | −20° / −50° / −60° |
| LiDAR の「前方」とみなす範囲 | 正面 ±15° |
| カメラの水平視野角 | 実測して決める |
| 問い合わせ上限 / 時間上限 | 40 回 / 600 秒 |

## 10. テスト方針
- TDD で進める。ROS や Gemini に依存しない計算（画像位置 → 旋回角度、Gemini の答えの読み取り、LiDAR の前方距離、状態の切り替え）を関数に分けてテストする
- 実機確認は「車輪を浮かせる → 床で短い距離 → 本番」の順に行う
- ロボットを動かさない確認は、トピック名を付け替えて行う（guide/04 と同じ方法）

## 11. 対象外（今回はやらない）
- 地図作り（SLAM）や、障害物を避けて回り込む経路計画
- 複数の目標を順に回る、など複雑な指示
- 学習（Gemini は推論のみで使う）
