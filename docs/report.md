# 言葉で指示できるロボット

Physical AI 応用1講座 最終課題 説明資料

- デモ動画：（YouTube の URL）
- コード：（GitHub リポジトリの URL）

## 1. 概要
「ピンクのテープのところへ行って」のように**言葉で指示する**と、ロボットが**自分でカメラを使って目標を探し、近づいて止まる**システムを、実機（Yahboom MicroROS-ESP32 ロボットカー）で実装した。

- 目標の発見と位置の推定には、ロボット向けの VLM **Gemini Robotics-ER 2**（推論のみ）を使う
- 移動と安全な停止は、オドメトリと LiDAR を使った自作の制御で行う

講座の課題サンプル「Gemini Robotics-ER 1.6を試す」（画像の中の物を指させる）を出発点にした。指させた結果を使って**実機を目標まで動かす**ところまで発展させている。

## 2. 目的
- 言葉と画像を一緒に理解できる VLM を、実際に動くロボットの「目と頭」として使う
- 実機で起きる問題（センサの死角・通信の遅れ・AI の遅さ）を、観測と記録をもとに一つずつ解決する

## 3. システム構成
```
カメラ ─画像────────▶┌──────── 制御ノード（ROS 2 / Python）────────┐
ロボット ─/odom_raw─▶│ 探す → 近づく → 見失ったら詳細に探す         │─/cmd_vel─▶ ロボット
LiDAR ─/scan───────▶│   └「見る」ときだけ ─画像＋指示─▶ Gemini     │─/beep────▶ ロボット
                     └──────────────────────────────────────────────┘
```
| 要素 | 内容 |
|---|---|
| ロボット | Yahboom MicroROS-ESP32（4輪、首振りカメラ 320×240、MS200 LiDAR、IMU） |
| 通信 | ロボット（micro-ROS）↔ micro-ROS Agent ↔ ROS 2 Humble。WSL2 + Docker で構築 |
| AI | Gemini Robotics-ER 2（`gemini-robotics-er-2-preview`）。画像と指示を送ると、目標の画像上の位置 `[y, x]` を返す |
| 制御 | Python（rclpy）のノード1つ。計算部分は関数に分けてテストした（pytest 30 件） |

### AI と制御の役割分担
- **AI（遅いが賢い、約3〜5秒）**：「目標は画像のどこにあるか」だけを答える
- **制御（速い、10Hz）**：画像上の位置を旋回角度に換算し、オドメトリで旋回・前進する。障害物の判定は LiDAR で行う

AI に直接モーターを動かさせず、**速度の上限や停止の判断は必ずコードで守る**ようにした。AI の誤りや遅れがあっても、安全が保たれる。

## 4. 動作の流れ
1. **探す**：正面の画像で目標を探す。見つからなければ、車体を一周させながら首を振って12枚撮り、**まとめて1回で AI に送る**。それでもなければ、LiDAR で空いている方向へランダムに移動する
2. **近づく**：目標の方向へ旋回し、前進する（遠ければ 30cm、近ければ 10cm ずつ）。大きく旋回したときは、進む前に見直して向きを確かめる
3. **見失った**：前進直後なら、まず足元を見る。それでもなければ、細かい角度で、カメラを上下にも振って36枚撮る**詳細探索**を行う
4. **到着**：目標が画像の下のほう（カメラが下向きなので＝目の前）に見えたら停止し、ブザーで知らせる

## 5. 開発の進め方
- **コーディングには AI（コーディング支援 AI の Claude Code）を使った**。設計の相談、コードの作成、テストの作成、不具合の原因調査を AI と対話しながら進めた。方針や仕様の判断、実機での動作の確認と評価は自分で行った
- **実機で動作を確認しながら進めた**。ロボットを走らせる → 記録（AI に送った画像・判断・停止理由）を確認する → 原因を特定する → 直す、を繰り返した（次章の表はその結果）
- 実機の前にシミュレーションで確かめる、といった検証はできていない。ロボットの性質（センサの死角、通信の遅れなど）も、実機を動かして初めてわかったものが多い
- ROS や AI に依存しない計算（画像の位置 → 旋回角度、LiDAR の距離、AI の答えの読み取りなど）は関数に分け、テストを先に書いてから実装した（pytest 30 件）

## 6. 工夫した点
実機で走らせては記録を確認し、見つかった問題を一つずつ直した。主なものを挙げる。

| 起きた問題 | 原因（記録・実測から特定） | 対策 |
|---|---|---|
| テープの手前で「到着」と判定した | 床の平たいテープは LiDAR の測定面より低く、映らない。奥の物を測っていた | 到着は**カメラ**で判断し、LiDAR は障害物での停止だけに使う |
| どの向きでも障害物と判定し、後退を繰り返した | 首振りカメラが −35° より上を向くと、カメラの頭が **LiDAR の正面を塞ぐ**（うなずき角を変えて実測） | 見るときだけカメラを上げ、動くときは −50° に下げる |
| 後ろの障害物で止まらなかった | LiDAR から車体の端までの距離が前後で違う（前 0.113 m、後ろ 0.135 m を実測） | 前後別々に、車体の端から 5cm で止まるようにした |
| 一周探索で見つけた方向に回っても、目標がない | カメラ画像は WiFi 経由で遅れて届き、動いた直後の画像は**動く前の向き**のものだった | 動き終わってから 1 秒以上後に届いた画像だけを使う |
| 近づくと目標を見失う | 近いほど視野が狭く、目標がカメラの下に外れる | 近いときは小刻みに進み、見失ったら足元を確認する |
| 探索が遅い | AI への問い合わせ1回に数秒かかる | 撮りためた画像を**まとめて1回で送る**（最大6回 → 1回） |
| 回数制限のエラーで、見ないまま旋回した | 無料枠は1分に5回まで。エラーを「見えない」扱いにしていた | エラー時は動かずに聞き直す |

### 安全とモニタリング
- `/cmd_vel` は最後の指令を保持し、1通だけだと WiFi で落ちることがある（実験で確認）。そこで、走行中は 10Hz で送り続け、終了時は**オドメトリで停止を確認できるまで**停止指令を送る
- Ctrl+C でも必ず停止する（ROS 2 Humble の標準の Ctrl+C 処理は、通信を先に閉じてしまい停止指令を送れなかった）
- センサが途絶えたとき、動作が時間内に終わらないときは安全停止する
- 講義の「症状 → 観測 → 比較 → 記録」に沿い、AI に送った画像・AI の答え・判断・停止理由を、実行ごとに記録する（`runs/<日時>/`。目標を見つけた画像には赤丸を描く）。上の表の原因は、すべてこの記録と実測から特定した

## 7. 結果
- 机の上で、ロボットから見えない位置に置いたテープを、探索 → 発見 → 接近 → 到着まで自律的に行えた
- 言葉の指示を変えるだけで、別の目標にも使える（コードの変更は不要）

## 8. 課題と今後
- 目標とロボットの間に障害物があると、回り込めない（経路計画は対象外とした）
- 想定状況ごとの網羅的な検証や、シミュレーションでの事前検証は、時間の都合で行えていない
- 動作は、自宅の広い机の上で人が監視しながら確認した（走行できる床がなかったため）。LiDAR では机の端（段差）を検知できないため、無人で走らせることはできない
- 今後：障害物の回り込み、「ボトルの左のテープ」のような位置関係を含む指示の評価、複数の目標を順に回る指示への対応
