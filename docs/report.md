# 言葉で指示できるロボット

Physical AI 応用1講座 最終課題 説明資料

## 1. 概要
「ピンクのテープのところへ行って」のように**言葉で指示する**と、ロボットが**自分でカメラを使って目標を探し、近づいて止まる**システムを、実機（Yahboom MicroROS-ESP32 ロボットカー）で実装した。

- 目標の発見と位置の推定：ロボット向けの VLM **Gemini Robotics-ER 2**（推論のみ）
- 移動と安全な停止：オドメトリと LiDAR を使った自作の制御（ROS 2）

講座の課題サンプル「Gemini Robotics-ER 1.6を試す」（画像の中の物を指させる）を出発点にし、指させた結果で**実機を目標まで動かす**ところまで発展させた。

## 2. 目的
- 言葉と画像を一緒に理解できる VLM を、実際に動くロボットの「目と頭」として使う
- 実機で起きる問題（センサの死角・個体差・信号のずれ・AI の遅さ）を、観測と記録をもとに一つずつ解決する

## 3. システム構成
```
カメラ ─画像────────▶┌──────── 制御ノード（ROS 2 / Python）────────┐
ロボット ─/odom_raw─▶│ 探す → 近づく → 見失ったら詳しく探す         │─/cmd_vel─▶ ロボット
LiDAR ─/scan───────▶│   └「見る」ときだけ ─画像＋指示─▶ Gemini     │─/beep────▶ ロボット
                     └──────────────────────────────────────────────┘
```
| 要素 | 内容 |
|---|---|
| ロボット | Yahboom MicroROS-ESP32（4輪、首振りカメラ 320×240、MS200 LiDAR、IMU） |
| 通信 | ロボット（micro-ROS）↔ micro-ROS Agent ↔ ROS 2 Humble。WSL2 + Docker で構築 |
| AI | Gemini Robotics-ER 2（`gemini-robotics-er-2-preview`）。画像1枚と指示を送ると、目標の画像上の位置 `[y, x]` を返す |
| 制御 | Python（rclpy）のノード1つ。調整するパラメータは `config.py` にまとめた |

### AI と制御の役割分担
- **AI（遅いが賢い。1回 約3〜5秒）**：「目標は画像のどこにあるか」だけを答える
- **制御（速い。10Hz）**：画像上の位置を旋回角度に換算し、オドメトリで旋回・前進する。障害物の判定は LiDAR で行う

AI に直接モーターを動かさせず、**速度の上限や停止の判断は必ずコードで守る**。AI が間違えたり遅れたりしても、安全は保たれる。

## 4. 動作の流れ
1. **探す**：正面の画像で探す。見つからなければ、車体を 30° ずつ回りながら1枚ずつ AI に聞き、見つかった時点で止まる。一周しても見つからなければ、LiDAR で十分に空いている方向からランダムに選んで少し移動する
2. **近づく**：目標が正面に来るよう旋回して前進する（遠ければ 30cm、近ければ 10cm ずつ）。大きく旋回したときは、進む前に見直す
3. **見失った**：前進直後なら、まず足元を見る。それでもなければ、30° ずつ回りながらカメラを上下にも振る**詳細探索**を行い、見つからなければ少しだけ動いて繰り返す
4. **到着**：目標が画像の下のほう（カメラは下向きなので＝目の前）に見えたら止まり、ブザーで知らせる

障害物が前にあれば少し下がり、目標を探している途中なら空いている方向へ向き直す。

## 5. 開発の進め方
- **コーディングには AI（コーディング支援 AI の Claude Code）を使った**。設計の相談、コードとテストの作成、不具合の原因調査を AI と対話しながら進めた。方針・仕様の判断と、実機での動作の確認・評価は自分で行った
- **実機で動作を確認しながら進めた**。走らせる → 記録を確認する → 原因を特定する → 直す、を繰り返した。次章の対策は、すべてこの繰り返しから生まれた
- 実機の前にシミュレーションで確かめるような検証はできていない。ロボットの性質の多くは、実機を動かして初めてわかった
- ROS や AI に依存しない計算（画像の位置 → 旋回角度、LiDAR の距離、AI の答えの読み取りなど）は関数に分け、テストを先に書いてから実装した（pytest 22 件）

## 6. 工夫した点
実機で見つかった問題を、テーマごとにまとめる。原因はいずれも、実行記録と実測から特定した。

### 6.1 センサの死角
| 起きた問題 | 原因 | 対策 |
|---|---|---|
| テープの手前で「到着」と判定した | 床の平たいテープは LiDAR の測定面より低く、映らない。奥の物を測っていた | 到着は**カメラ**で判断し、LiDAR は障害物での停止だけに使う |
| どの向きでも障害物と判定し、後退を繰り返した | カメラが −35° より上を向くと、カメラの頭が **LiDAR の正面を塞ぐ**（うなずき角を変えて実測） | 見るときだけカメラを上げ、動くときは −50° に下げる |
| 近づくと目標を見失う | 近いほど視野が狭く、目標がカメラの下に外れる | 近いときは小刻みに進み、見失ったら足元を確認する |

### 6.2 個体差と仮定の値の見直し
| 起きた問題 | 原因 | 対策 |
|---|---|---|
| 後ろの障害物で止まらなかった | LiDAR から車体の端までの距離が前後で違う（前 0.113 m、後ろ 0.135 m を実測） | 前後別々に、車体の端から 5cm で止まるようにした |
| 一周探しても写らない方向があった | カメラの視野角を 60° と仮定していたが、首振り前後の画像のずれから実測すると約 41° だった | 視野角を 41° に直し、回る角度を視野角より小さく（30°）して隙間をなくした |
| 首振りが左に偏っていた | 首振りサーボの 0° が、車体の正面から左に約 30° ずれていた | サーボに送る値に補正値を足し、本当の正面を 0° とした |

### 6.3 信号の同期（講義で扱われた問題）
| 起きた問題 | 原因 | 対策 |
|---|---|---|
| 見つけた方向へ回っても、目標がない | ① カメラ画像は WiFi 経由で遅れて届き、動いた直後の画像は**動く前の向き**のものだった ② 一時は「首を振って撮りためた画像をまとめて送り、撮影時の向きと首の角度から方向を逆算する」方式にしていたが、首振りが画像に反映されないことがあり、逆算が大きくずれた（サーボは今の角度を報告しないため、確かめられない） | ① 動き終わってから 1 秒以上後に届いた画像だけを使う ② 首を正面に固定し、少しずつ回りながら1枚ずつ聞いて、**見つかった時点で止まる**方式に変えた。目標は「今の正面の画像の中」にあるので、逆算が要らない（**同期が要らない設計で回避した**） |

### 6.4 AI の使い方
| 起きた問題 | 原因 | 対策 |
|---|---|---|
| 見ないまま旋回した | API の回数制限（無料枠は1分に5回）のエラーを「見えない」扱いにしていた | エラー時は動かずに聞き直す |
| AI の答えをプログラムで読めない | 答えが `` ```json `` で囲まれていることがあった | 答えの中の JSON 部分だけを読む。読めなければ「見えない」とする |

### 6.5 安全とモニタリング
- `/cmd_vel` は最後の指令を保持し、1通だけだと WiFi で落ちることがある（実験で確認）。そこで、走行中は 10Hz で送り続け、終了時は**オドメトリで停止を確認できるまで**停止指令を送る
- Ctrl+C でも必ず停止する（ROS 2 Humble の標準の Ctrl+C 処理は通信を先に閉じてしまい、停止指令を送れなかった）
- センサが途絶えたとき、動作が時間内に終わらないとき、障害物で続けて止まったときは安全に終了する
- 講義の「症状 → 観測 → 比較 → 記録」に沿い、AI に送った画像・AI の答え・判断・止まった理由を実行ごとに記録する（目標を見つけた画像には赤丸を描く）。6.1〜6.4 の原因は、すべてこの記録と実測から特定した

## 7. 結果
- 机の上で、ロボットから見えない位置に置いたテープを、探索 → 発見 → 接近 → 到着まで自律的に行えた
- 言葉の指示を変えるだけで、別の目標にも使える（コードの変更は不要）
- 成功率などの定量的な評価は行えていない

## 8. 課題と今後
- 目標とロボットの間に障害物があると、回り込めない（経路計画は対象外とした）
- 想定状況ごとの網羅的な検証や、シミュレーションでの事前検証は、時間の都合で行えていない
- 動作は、自宅の広い机の上で人が監視しながら確認した（走行できる床がなかったため）。LiDAR では机の端（段差）を検知できないため、無人では走らせられない
- 今後：障害物の回り込み、「ボトルの左のテープ」のような位置関係を含む指示の評価、複数の目標を順に回る指示への対応
